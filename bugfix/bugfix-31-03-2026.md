## Task 1 — Real stage не разбивается на несколько при последовательных OUT → IN

**Файл:** `SequenceEngineServiceImpl.java`
**Метод:** `handleInTrigger`

### Симптом
Parking `2026-03-17 13:01:22 → 2026-03-19 10:31:58` (45ч) записан как один этап вместо 4 отдельных.
cam20 несколько раз выдавал OUT (dir≈180) а потом снова IN (dir≈360) — все игнорировались.

### Причина
Условие дедупликации не проверяет `outTime`:

```java
// ТЕКУЩИЙ КОД — НЕВЕРНО:
if (activeStage != null && activeStage.getName().equals(match.stageName)
        && activeStage.getInTime() != null) {
    return; // игнорирует IN даже после того как был OUT
}
```

По spec: если у активной стадии уже есть `outTime` (последнее событие было OUT), следующий IN должен **закрыть текущую стадию и открыть новую**. Дедупликация должна срабатывать только если после открытия стадии ещё не было OUT.

### Исправление

```java
// ИСПРАВЛЕННЫЙ КОД:
if (activeStage != null && activeStage.getName().equals(match.stageName)
        && activeStage.getInTime() != null
        && activeStage.getOutTime() == null) {  // <- добавить это условие
    log.debug("Dedup: in trigger for already-active stage '{}' plate={}", match.stageName, plate);
    return;
}
// Если outTime != null — не возвращаемся; код ниже закроет стадию и откроет новую
```

Остальная логика метода (закрытие предыдущей стадии + открытие новой) уже написана корректно и заработает сама.

## Task 2 — `checkTransitionalAutoStart` не вызывается при смене стадии через OUT-триггер

**Файл:** `SequenceEngineServiceImpl.java`
**Метод:** `handleOutTrigger`

### Симптом
После исправления Task 1: когда Parking закрывается OUT-триггером другой стадии (ветка «different stage»), авто-старт Backyard не создаётся. `checkTransitionalAutoStart` вызывается только в ветке «same stage».

### Причина

```java
// ТЕКУЩИЙ КОД в ветке «different stage» — нет вызова checkTransitionalAutoStart:
if (activeStage != null) {
    invalidateCandidates(seq, detection.getCreatedAt());
    if (activeStage.getOutTime() != null) {
        closeActiveStage(activeStage, null);
    } else {
        closeActiveStage(activeStage, detection.getCreatedAt().minusSeconds(1));
    }
    // <- здесь нет checkTransitionalAutoStart
}
Stage partial = createPartialStage(match, plate, detection.getCreatedAt());
```

### Исправление

Добавить вызов `checkTransitionalAutoStart` после закрытия стадии:

```java
if (activeStage != null) {
    invalidateCandidates(seq, detection.getCreatedAt());
    if (activeStage.getOutTime() != null) {
        closeActiveStage(activeStage, null);
    } else {
        closeActiveStage(activeStage, detection.getCreatedAt().minusSeconds(1));
    }
    // NEW: trigger auto-start for transitional stages that follow the closed stage
    if (activeStage.getOutTime() != null) {
        checkTransitionalAutoStart(seq, activeStage, activeStage.getOutTime());
    }
}
Stage partial = createPartialStage(match, plate, detection.getCreatedAt());
```

## Task 3 — Sequence close timeout не закрывает последовательность при историческом rebuild

**Файл:** `SequenceEngineServiceImpl.java`
**Методы:** `checkAndCloseForDetectionGap`, `insertHistoricalTransitionals`

### Симптом

**3a.** KA8611PK: Backyard (id=79) длился ~77ч. `sequenceCloseTimeoutOverrideMinutes=2880` (48ч) для Backyard — последовательность должна была закрыться через 48ч и открыться новая.

**3b.** KA8611PK / KA2654TA: разрывы между детектами > 2880мин (глобальный таймаут) не всегда закрывают последовательность при историческом rebuild.

### Причина 3a

При историческом rebuild `performMaintenance` не вызывается между детектами — кандидаты не материализуются. Backyard-кандидат создан, но `getActiveStage()` возвращает предыдущий real stage (Parking), не Backyard. Поэтому в `checkAndCloseForDetectionGap` ветка с проверкой `sequenceCloseTimeoutOverrideMinutes` не достигается — `activeStage.getType()` не равен "transitional".

### Исправление 3a

В `checkAndCloseForDetectionGap` добавить проверку pending candidates перед non-transitional блоком:

```java
// ADD after the transitional activeStage block, before the non-transitional block:

// Check pending transitional candidates with override timeout
for (Stage candidate : seq.getCandidates()) {
    if (candidate.getSequenceCloseTimeoutOverrideMinutes() > 0
            && candidate.getInTime() != null) {
        long minutesSinceCandidate =
            Duration.between(candidate.getInTime(), detectionTime).toMinutes();
        if (minutesSinceCandidate >= candidate.getSequenceCloseTimeoutOverrideMinutes()) {
            log.debug("Closing sequence for plate={}: candidate '{}' override timeout {}min exceeded",
                    plate, candidate.getName(),
                    candidate.getSequenceCloseTimeoutOverrideMinutes());
            closeSequence(plate, detectionTime);
            return;
        }
    }
}

// Non-transitional: global timeout measured from last detection
long minutesSinceLastDetection = ...
```

### Причина 3b

`insertHistoricalTransitionals` вставляет transitional если gap > `candidateTimeoutMinutes`, но не проверяет не превышает ли gap sequence close timeout. Если gap превышает таймаут — последовательность должна была закрыться; вставлять transitional через этот gap нельзя.

### Исправление 3b

В `insertHistoricalTransitionals`, после вычисления `gapSeconds`, перед созданием `Stage transitional`:

```java
long gapSeconds = Duration.between(stageA.getOutTime(), stageB.getInTime()).toSeconds();
if (gapSeconds > (long) tc.getCandidateTimeoutMinutes() * 60) {

    // NEW: skip if gap exceeds the effective sequence close timeout
    long overrideMinutes = tc.getSequenceCloseTimeoutOverrideMinutes();
    long effectiveCloseTimeoutSeconds = (overrideMinutes > 0
            ? overrideMinutes
            : wf.getSequenceCloseTimeoutMinutes()) * 60L;

    if (gapSeconds >= effectiveCloseTimeoutSeconds) {
        log.debug("Gap {}s >= close timeout {}s for '{}' plate={}: skipping historical transitional",
                gapSeconds, effectiveCloseTimeoutSeconds, tc.getName(), seq.getPlateNumber());
        continue;
    }

    // existing code: create and insert transitional stage
    Stage transitional = new Stage();
    ...
}
```

**Примечание:** разбивка самих последовательностей (создание новой PlateSequence после закрытой) обрабатывается через `checkAndCloseForDetectionGap` (Task 3a) — к моменту вызова `insertHistoricalTransitionals` последовательности уже корректно закрыты. В `insertHistoricalTransitionals` достаточно только **не вставлять** transitional через закрытый gap.

## Task 4 — `full=true` для partial stage

**Файл:** `SequenceEngineServiceImpl.java`
**Методы:** `createPartialStage`, все места вызова `stage.setFull(true)`

### Симптом
KA2654TA id=853 в БД: `in_time=null`, `out_time=2026-03-29 15:04:24`, `full=true`. По spec partial stage (`inTime=null`) всегда должен иметь `full=false`.

### Причина
Где-то после создания partial-стадии выставляется `full=true` без проверки что `inTime != null`. Скорее всего в `materializeCandidates` или в одном из путей закрытия стадии.

### Исправление

1. В `createPartialStage` убедиться что `full=false` и добавить комментарий:
```java
partial.setFull(false);  // partial stage: no inTime yet, cannot be full
partial.setInTime(null); // always null for partial
partial.setOutTime(outTime);
```

2. Найти все места в коде где вызывается `stage.setFull(true)` и добавить guard:
```java
// Before any setFull(true) call:
if (stage.getInTime() == null) {
    log.warn("Attempted to set full=true on partial stage '{}' plate={} — skipping",
            stage.getName(), stage.getPlateNumber());
    // do not set full=true
}
```

3. В `materializeCandidates` — кандидаты всегда имеют `inTime` (выставляется при создании), поэтому там `setFull(true)` корректен. Проверить только остальные пути.
