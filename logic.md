# ALPR Sequence Engine — Technical Specification

## Overview

A Spring Boot application that reads ALPR (Automatic License Plate Recognition) detections from a source PostgreSQL database, processes them into sequences and stages, and writes results to a target PostgreSQL database.

On startup it creates all required tables in the target DB if they do not exist.

---

## General Points

1. Get detections for the specified period (from a certain date to now).
2. Build retro sequences.
3. Define active sequences.
4. Update detections from the source table every N seconds (configurable).
5. Maintain sequences and timing.
6. Send alerts in defined cases.

## Logic

The application is a state engine that does the following:

1. Gets all detections for a given license plate.
2. Builds a sequence of stages the plate passed through.
3. Counts the time the plate spent at each stage.
4. Creates alarms in certain cases.
5. Marks a sequence as closed and starts a new one in certain cases.

There can be several stages of the same type and with the same name in one sequence.

The application must correctly calculate stages and timing both post-factum (for historical data) and in real time (for active sequences). The logic must work correctly for all plates regardless of how long ago they were first detected.

## Database Rules

### Source Database

- Fetch **all** detections on the first connection.
- Refresh every `sourceRefreshSeconds` seconds, fetching only detections newer than the last processed timestamp.

#### Source Table DDL

```sql
CREATE TABLE videoanalytics.alpr_detections (
    id int8 GENERATED BY DEFAULT AS IDENTITY(...) NOT NULL,
    plate_number varchar(15) DEFAULT '' NOT NULL,
    arabic_number varchar(64) DEFAULT '' NOT NULL,
    adr varchar(10) DEFAULT '' NOT NULL,
    box text NULL,
    plate_image text NULL,
    frame_image text NULL,
    analytics_id int4 NOT NULL,
    make_model_id int4 DEFAULT -1 NOT NULL,
    vehicle_type int4 DEFAULT 1 NOT NULL,
    created_at timestamp(3) NOT NULL,
    color_id int4 NULL,
    direction int4 NULL,
    country varchar(5) NULL,
    pattern varchar(100) NULL,
    client_id int4 DEFAULT 0 NOT NULL,
    latitude numeric(9, 6) DEFAULT 0 NULL,
    longitude numeric(9, 6) DEFAULT 0 NULL,
    CONSTRAINT alpr_plates_pkey PRIMARY KEY (id)
);
```

> **Timezone:** `created_at` is stored in UTC. The application must treat all timestamps as UTC and perform all comparisons and duration calculations in UTC. `LocalDateTime.now()` calls must use `ZoneOffset.UTC`.

### Target Database

- The application uses root credentials from `config.json` to bootstrap the target database.
- **Bootstrap sequence on startup:**
  1. Connect using `rootUser` / `rootPassword` to the `maintenanceDb`.
  2. Create the target database if it does not exist.
  3. Create the target schema if it does not exist.
  4. Create the target user if it does not exist and grant it all privileges on the schema.
  5. Connect to the newly created database using the credentials already provided in the `sequence` block.
  6. Create all required tables (sequences, stages, alerts) if they do not exist.
- Update data after each source refresh.
- Write sequence and stage data to the stages table; write alert data to the alerts table.

> **Restart policy:** On every restart the application ignores the target DB entirely, re-fetches all detections from the source, and rebuilds all state from scratch. The target DB is a write-only output cache — it is never read on startup.

## Direction Matching

### Circular Arithmetic

Direction values are integers from 0 to 359 degrees. **Direction comparison is circular — 0° and 360° are the same point.** The angular distance between two directions is always the shortest arc around the circle.

Formally: `angularDistance(a, b) = min(|a - b|, 360 - |a - b|)`

A detection matches a trigger's direction if `angularDistance(detectedDirection, configuredDirection) <= 90`.

**Example:** configured direction = 300, tolerance = 90.  
Matching range: 210–360 and 0–30 (wrapping around 0°).

### Omitted Direction Field

If the `direction` field is omitted from a trigger, direction is irrelevant — any detected direction matches that trigger.

### In/Out Conflict Resolution on the Same Camera

A conflict occurs when an `in` trigger and an `out` trigger on the **same `analyticsId`** have overlapping direction ranges (i.e. there exists at least one direction value matched by both).

When a conflict is detected:

- The `out` trigger's range is expanded by 1° on each boundary that overlaps with the `in` trigger, giving it a 182° range.
- The `in` trigger's range is correspondingly shrunk to 178° on the conflicting side.
- The `out` trigger always takes priority for any direction that falls within both ranges.

## Stage Type: Real

### Configuration Fields

| Field      | Description                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------ |
| `name`     | Internal name for reuse                                                                          |
| `label`    | Public name shown in reports                                                                     |
| `triggers` | Array of trigger objects. Each has `type` (`in`/`out`), `analyticsId`, and optional `direction`. |

### Database Fields

| Field      | Description                |
| ---------- | -------------------------- |
| `id`       | Primary key                |
| `timeout`  | Always `0` for real stages |
| `active`   | `true` / `false`           |
| `full`     | `true` / `false`           |
| `plate`    | License plate number       |
| `inTime`   | Stage start timestamp      |
| `outTime`  | Stage end timestamp        |
| `duration` | Elapsed time               |
| `alarms`   | Associated alarms list     |

### Cold-Start Rule (First Detection for a Plate)

When the very first detection ever seen for a plate is an **out** trigger:

- Create a partial stage with `inTime = null`, `outTime = detectionTimestamp`, `full = false`.
- This follows the standard partial stage policy from that point forward.

When the very first detection is an **in** trigger, open a normal stage as described below.

### In Policy

- All `in` events are deduplicated if the same stage is already active.
- **Active sequences:** if the last event for this stage was `in` and the next is also `in`, ignore it.
- **Historical sequences:** if multiple consecutive `in` events appear (with no `out` or other stage events between them), only the first `in` opens the stage.
- If a stage is closed (by an `out` event or by another stage opening), the next `in` opens a new instance of that stage type.

### Out Policy

- Each subsequent `out` event overwrites the stage's `outTime`.
- **Active sequences:** if the last event was `out` and the next is also `out`, overwrite `outTime` in the target DB.
- **Historical sequences:** if multiple consecutive `out` events appear (with no `in` or other stage events between them), only the last `out` is used as the closing time.

### Full Stage Policy

- Full stages have both `inTime` and `duration` populated from the start.
- On each DB refresh, recalculate `duration` for every active stage:
  - If stage has no `outTime`: `duration = now(UTC) - inTime`
  - If stage has `outTime`: `duration = outTime - inTime`

### Partial Stage Policy

- If stage A is active **with** `outTime` and the next detection is an `out` trigger for stage B:
  - Close stage A using its current `outTime`.
  - Open partial stage B with `inTime = null`, `outTime = detectionTimestamp`, `full = false`.

- If stage A is active **without** `outTime` and the next detection is an `out` trigger for stage B:
  - Close stage A with `outTime = detectionTimestamp - 1 second`.
  - Open partial stage B with `inTime = null`, `outTime = detectionTimestamp`, `full = false`.

- If the next trigger after the partial B open is also an `out` for stage B:
  - Set stage B `inTime = stage B's first outTime`.
  - Overwrite stage B `outTime` with this new detection timestamp.
  - Stage B is now treated as a full stage and duration can be calculated.

- **Historical sequences:** if you encounter an `in` for stage A followed directly by an `out` for stage B, create a full stage A (`inTime` from the `in` event, `outTime = B's out timestamp - 1 second`) and a partial stage B (`inTime = null`, `outTime = B's out timestamp`).

### Active Policy

- A stage is active until the next stage's `in` trigger fires.
- No changes may be made to an inactive stage.
- If a stage remains active for `sequenceCloseTimeoutMinutes` with no new detections, it closes with `outTime = null` and `duration = null`.

## Stage Type: Transitional

### Configuration Fields

| Field | Description |
|---|---|
| `name` | Same as real stage |
| `label` | Same as real stage |
| `triggers` | Same as real stage |
| `allowedAfter` | Array of stage names after which this transitional may auto-start |
| `candidateTimeoutMinutes` | Minutes after previous stage `out` before the transitional materializes |
| `sequenceCloseTimeoutOverrideMinutes` | If > 0, overrides global `sequenceCloseTimeoutMinutes` for this stage; if 0, use global value |

### Database Fields

Same as real stage, except:

| Field | Description |
|---|---|
| `timeout` | Initialized to `candidateTimeoutMinutes`; decremented on each refresh |

### In Policy — Camera Trigger

- Same deduplication rules as real stage `in` policy.

### In Policy — AllowedAfter Auto-Start (Candidate)

When an `out` event occurs for a stage listed in `allowedAfter`:

1. Create a **candidate** transitional stage in the DB with `inTime = stageA.outTime + 1 second` and `timeout = candidateTimeoutMinutes`. Candidates are stored in the DB but do not appear in reports.
2. On each target DB refresh, subtract the refresh interval (seconds) from `timeout` for all candidates.
3. When `timeout <= 0`, the candidate **materializes**: `full = true`, `duration = now(UTC) - inTime`.
4. Materialization automatically closes the previous real stage if it is still active.

**Candidate invalidation rules:**
- If the stage A `out` trigger fires again before the candidate materializes, apply the real stage out policy (overwrite `outTime`) and **reset the candidate timeout** to `candidateTimeoutMinutes`.
- If **any other detection** for the plate arrives before timeout ends (on any camera, any stage), the candidate is **deleted** without materializing.
- If a partial stage is created while a candidate is pending, the candidate is also deleted.

**Historical sequences:** After calculating stage A's `inTime`, `outTime`, and `duration`, if stage A is in `allowedAfter` for a transitional C, and the next detection for this plate (stage B `in`) arrives more than `candidateTimeoutMinutes` after stage A's `outTime`, create transitional stage C between A and B: `inTime = stageA.outTime + 1 second`, `outTime = stageB.inTime - 1 second`.

### Out Policy

- The start (or partial creation) of any other stage closes the transitional with `outTime = newStage.inTime - 1 second`.
- Creating a partial after a transitional may also create a new transitional candidate; the existing transitional candidate is deleted if a partial was created before it materialized.
- Transitional stages may also have their own `out` triggers; in that case they follow the same out policy as real stages.

### Active Policy

- Transitional stage remains active until closed.
- While active: `duration = now(UTC) - inTime`.
- After closed: `duration = outTime - inTime`.

### Sequence Close During Transitional

- If the sequence closes while a transitional candidate is still pending (not yet materialized), **delete the candidate** from the DB without materializing it.
- If `sequenceCloseTimeoutOverrideMinutes > 0` and the transitional triggers the sequence close, **remove the transitional stage itself** from the DB.
- If `sequenceCloseTimeoutOverrideMinutes = 0`, the global `sequenceCloseTimeoutMinutes` applies and the same removal rule applies when it fires via a transitional.

## Stage Type: Single Camera

### Configuration Fields

| Field | Description |
|---|---|
| `name` | Same as real stage |
| `label` | Same as real stage |
| `analyticsId` | The analytics camera ID. No direction check is performed. |

### Database Fields

Same as real stage (`timeout` is always `0`).

### In Policy

- The **first** detection of the plate on the specified `analyticsId` is the `in` event.

### Out Policy

- The **last** detection in a consecutive run on that camera is the `out` event (updated on each new detection).
- Single camera stages **cannot** trigger transitional auto-start.

### Active Policy

- Stage remains active until the next stage starts.
- In both states: active and inactive: `duration = outTime - inTime`.
- When the sequence closes while a single camera stage is active, the last detection is used as `outTime` and `duration = outTime - inTime`.

## Alerts

### Configuration Fields

| Field                | Description                                                                 |
| -------------------- | --------------------------------------------------------------------------- |
| `trigger`            | Trigger object without `type`. Has `analyticsId`, and optional `direction`. |
| `message`            | The message to send                                                         |
| `sendTimeOutMinutes` | Minutes to wait before sending                                              |
### Database Fields

| Field | Description |
|---|---|
| `id` | Primary key |
| `plate` | License plate |
| `timeout` | Initialized to `sendTimeOutMinutes`; decremented on each refresh |
| `message` | Alert message |
| `active` | `true` / `false` |

### Policy

1. When a detection matches an alert trigger's `analyticsId`, create an alert row with `timeout = sendTimeOutMinutes` and `active = true`. Only create the alert if there is an **active stage** for that plate and that trigger's `analyticsId`.
2. On each DB refresh, subtract the refresh interval (seconds) from `timeout` for all active alerts.
3. When `timeout <= 0`, send the alert message as: `"<plate>: <message>"` and set `active = false`.
4. If during the countdown the plate is detected on **any other `analyticsId`** (not the trigger one), set `active = false` immediately — do not send.
5. **Repeated triggers:** if a detection arrives for a plate that already has an active alert on that same `analyticsId`, ignore it — do not create a new alert row and do not reset the timeout.
6. Once `active = false`, the alert is never modified again.

## Reports

Reports are accessible as downloadable XLSX files. Each report is also saved to the directory specified in `reportsDir`.

### Endpoints

- `GET /report/sequences.xlsx` — full report for all loaded detections.
- `GET /report/sequences.xlsx/{dd-MM-yyyy}` — report filtered to the specified day.

> **Date filter scope:** The date filter includes all sequences that were **active at any point during that calendar day** (UTC). A sequence is considered active on a day if its start time is before the end of that day and its close time (if any) is after the start of that day.

### Sheet 1: Sequences (Active)

Shows active sequences grouped by plate. The first row of each sequence group shows the plate number in the central column.

| Column | Description |
|---|---|
| Stage | Stage label |
| In Time | `inTime` formatted timestamp |
| Out Time | `outTime` formatted timestamp |
| Duration | Human-readable duration |
| Alerts | Comma-separated list of alert messages associated with this stage, or empty |

### Sheet 2: Sequences (Closed)

Same structure as Sheet 1, but for closed sequences.

### Sheet 3: Events

All stages from all sequences sorted by `inTime` descending (newest first), not grouped by plate.

| Column | Description |
|---|---|
| Stage | Stage label |
| In Time | `inTime` formatted timestamp |
| Out Time | `outTime` formatted timestamp |
| Duration | Human-readable duration |
| Alerts | Comma-separated list of alert messages for this stage, or empty |

> **Candidates in reports:** Transitional candidate stages (not yet materialized, `timeout > 0`) are excluded from **all** report sheets.

## Global Rules

### Sequence

- One plate = one active sequence at a time.
- The first detected valid stage starts a sequence.
- A "valid stage" is any detection that matches an `in` trigger for any configured stage type, or an `out` trigger (which opens a partial stage, per the cold-start rule).

### Sequence Close Conditions

A sequence closes when:

- No detections have been received for the plate for `sequenceCloseTimeoutMinutes` (global), **or**
- The active transitional stage has `sequenceCloseTimeoutOverrideMinutes > 0` and that duration has elapsed since the transitional stage started.

**On close:**

| Active stage type | Behavior |
|---|---|
| Real stage | Saved with `outTime = null` and `duration = null` |
| Single camera stage | Saved with `outTime = lastDetectionTimestamp`, `duration = outTime - inTime` |
| Transitional (via override timeout) | The transitional stage is **removed** from DB; candidate stages are also deleted |
| Transitional candidate (pending) | Deleted without materializing |

### Stage Interaction

- Only one stage is active at a time per plate.
- Any new stage start closes the previous active stage by the rules defined above.
- **Transitional candidates** (stages with `timeout > 0` that have not yet materialized) are **not considered active stages**. They do not block new stages from opening and are not subject to the "one active stage at a time" rule. Only materialized stages (`timeout <= 0`) count as active.
- If a new stage opens while a candidate is pending, the candidate is deleted — see _Candidate invalidation rules_ above.

### Consistency Rules

- No overlapping stages for the same plate.
- No transitional stages shorter than `candidateTimeoutMinutes`.
- The timeline remains continuous until a sequence closes.

## Startup / Restart / Rebuild Policy

### Startup (First Run)

1. Bootstrap target DB (create database, schema, user, tables if needed).
2. Read **all** detections from source, sorted by `created_at` ascending.
3. Build all sequences, stages, and alerts from scratch.
4. Save everything to target DB.
5. Save `lastProcessedTimestamp` in memory.

### Runtime (Polling)

Every `sourceRefreshSeconds`:

1. Read detections where `created_at > lastProcessedTimestamp`.
2. Apply incrementally to current state.
3. Decrement timeouts for all transitional candidates and active alerts. Timeout decrements happen after new detections are applied so that an incoming detection can invalidate a candidate before it would have materialized.
4. Recalculate `duration` for all active stages.
5. Materialize any candidates whose `timeout <= 0`.
6. Send any alerts whose `timeout <= 0`.
7. Update target DB.
8. Update `lastProcessedTimestamp`.

### Restart

1. Ignore target DB entirely.
2. Re-fetch all detections from source.
3. Rebuild everything from scratch (same as first run).

> `lastProcessedTimestamp` is kept in memory only and is never persisted. It is always rebuilt from the source data on restart.
